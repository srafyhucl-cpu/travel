# tripPlan · 行程编辑（旅行助手）

> 写 SKILL：新建行程项、修改日期/标题/时间/地点/备注、勾选待办、删除行程项。
> 查询请走 tripItinerary；打卡请走 tripCheckin；记账请走 tripMoney。

## 业务流程图

```
用户意图
  │
  ├─ 加一项安排（"明天 9 点加个早餐"）─────────────→ createItem
  │     （date/title 必填；时间/地点/备注/待办只有用户说了才传）
  │
  ├─ 改已有安排（"把雪山改到 15:00"）
  │     │
  │     ├─ 上下文里没有该行程项 nodeId？
  │     │     先查后改：getDaySchedule（知道哪天）/ findItems（知道名字）
  │     │     ← 用 tripItinerary 的查询接口拿到 nodeId 再继续
  │     │
  │     └─ updateItem（只传用户本轮明确提到的字段，没提的一律不动）
  │
  ├─ 勾 / 取消待办（"充电宝带上了 / 身份证不用带"）
  │     │
  │     ├─ 没有 itemId / itemText？先查：getTodos 拿最新原文
  │     │
  │     └─ setTodo（nodeId + itemText 或 itemId + done）
  │
  └─ 删一项（"把 XX 删掉"）
        │
        ├─ 用户本轮没有明确说"删"？──── 不调用任何接口，如实回复
        │
        ├─ 先查后删：findItems / getDaySchedule 拿到 nodeId 与准确名称
        │
        ├─ 本轮只复述："要删除的是「XX」（某天某时），确认吗？" ← 禁止调用 deleteItem
        │
        └─ 用户下一轮确认后才调用 deleteItem（title 一字不差，否则拒绝）
```

所有写操作成功后返回「文本确认 + 小程序卡片」：点击卡片接力进时间线（带 `date=` 时定位到当天）。

## 原子接口 ↔ 接力页映射

| 接口 | 用途 | handoff.query | 接力页 |
|------|------|---------------|--------|
| createItem | 新建行程项 | `date=YYYY-MM-DD` | /pages/timeline/index |
| updateItem | 改日期/标题/时间/地点/备注 | `date=新日期` | /pages/timeline/index |
| setTodo | 勾选 / 取消勾选待办 | 按天项带 `date=`；出行准备为空 | /pages/timeline/index |
| deleteItem | 删除行程项 | 空 | /pages/timeline/index |

## 业务约束（跨接口铁律）

### 0. 能力边界（最高优先级）

- 本 SKILL 的全部能力就是上面 4 个接口：新建 / 修改 / 勾待办 / 删除**单个**行程项。
- 不支持：批量新建或删除、整体重排/顺延、复制行程、给已有项新增待办条目、删除单条待办、撤销删除、修改打卡记录、记账。用户要这些 → 如实说暂不支持，能转其它 SKILL 的转过去，不能的引导打开小程序操作；禁止硬凑接口或假装完成。
- 只有当用户意图能明确对到某个接口的真实语义时才调用；对不上就如实回复，不要编参数、不要假装完成。
- 分工：**查询走 tripItinerary**（getDaySchedule / findItems / getTodos / getTripOverview）、**打卡走 tripCheckin**（checkIn）、**记账走 tripMoney**；本 SKILL 只负责编辑。

### 1. 先查后改（铁律）

- nodeId 必须来自 getDaySchedule / findItems / getTodos 的返回原文；禁止猜、禁止拿行程项名字当 ID、禁止使用示例值。
- 改已有项、勾待办、删除之前，上下文里没有 nodeId 就先查一次；不要对"大概那一条"动手。
- 查询出现多个相似项时，先和用户确认是哪一条，再调用写接口。

### 2. 只改用户明确提到的字段

- updateItem 只传用户本轮明确说要改的字段；没提到的字段（哪怕你知道原值）一律不传，不要"顺手对齐"。
- 例："把雪山开始时间改到 15:00" → 只传 startTime，结束时间保持不动；"改个名字叫苍山索道" → 只传 title。
- 时间格式：24 小时制 HH:mm（如 09:00 / 15:30）；日期 YYYY-MM-DD；"今天/明天/下午两点"都要先换算成确定值，拿不准先问。
- 改动完成后只复述实际改过的字段；没改的不要提，也不要编造。

### 3. 删除铁律

- 只有用户明确表达删除意图（"删掉 / 不要了 / 去掉 XX"）才可能删除；"整理一下"这类模糊说法一律不触发。
- **两步确认（铁律）**：即使用户本轮已经明确点名要删，本轮也只复述（名称 + 日期时间）并等待用户再次确认，
  **复述的这一轮禁止调用 deleteItem**；只有用户下一轮明确确认（"确认 / 删吧 / 对"）才调用。
  唯一例外：用户在同一句话里明确表示无需确认（如"直接删掉，不用问了"）。
- 调用时 title 必须与实际名称一字不差，接口会用这个做防误删硬校验。
- 一次只删一项；用户要删多项 → 逐项复述、逐项确认、逐项调用。
- 删除后找不回来：如实说「已删除」，不要暗示可以恢复，也不要"顺手"重建。

### 4. 防编造

- 所有 ID（nodeId / itemId）一律用上游接口返回的原文；没有就先去查。
- 新建项的标题、地点、备注取自用户原话；用户没说的字段不要自作主张补，也不要替用户"润色"出新信息。
- 数字与时间不猜：用户说得含糊（"下午晚一点""玩两个小时"）→ 先问清楚再写。

### 5. 结果与错误处理

- 接口失败时按 content 里的事实和出口处理（例如"请先 getTodos 查最新 itemId/itemText"），不要用同样的参数重复调用。
- setTodo 返回 noop（已是目标状态）不算失败：如实告诉用户"已经是这个状态"，不要再调一次。
- 删除成功后的卡片回时间线；不要用文字复述已删除项以外的内容。

## 用户意图分流

| 用户说法 | 动作 |
|---|---|
| "明天 9 点加个早餐 / 新增 XX" | createItem（date/title 必填） |
| "把 XX 改到 15:00 / 改名叫 XX / 换个地点 / 挪到后天" | 先查 nodeId → updateItem（只传要改的字段） |
| "XX 带上了 / 把 XX 勾掉" | 先 getTodos（或用上下文里的 itemId）→ setTodo(done=true) |
| "XX 不用带了 / 取消勾选" | setTodo(done=false) |
| "把 XX 从行程里删掉" | 先查 → 本轮复述、下一轮确认 → deleteItem |
| "今天还有什么安排 / XX 是哪天 / 待办还有啥" | 转 tripItinerary |
| "我们到 XX 了 / XX 完成了" | 转 tripCheckin |
| "记一笔 / 花了多少 / 改账删账" | 转 tripMoney |
| "取消打卡 / 顺延时间 / 批量整理 / 给已有项加一条待办" | 本 SKILL 不支持，如实说明并引导打开小程序操作 |
| 与行程无关的问题（天气、订票等） | 如实说不属于本小程序的能力，不要编 |
